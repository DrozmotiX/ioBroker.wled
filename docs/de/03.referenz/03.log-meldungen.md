## Was bedeutet die Warnung "State attribute definition missing"?

<!-- abschnitt: prio=A; gewicht=11; readme=missing; cluster=logs-install-01; features=log-missing-attribute,state-attribute-library -->
<!-- muss beantworten: Erklärt, dass es nur eine Debug-Meldung zu unbekannten Feldern ist, und ab welcher Version. -->

**Kurz:** Die Meldung ist harmlos, du musst nichts tun. WLED liefert ein Feld, für das der Adapter keine eigene Beschreibung hat. Der Adapter legt den Datenpunkt trotzdem an. Seit v0.7.1 steht die Meldung nur noch auf der Log-Stufe „debug“.
<!-- quelle: code=main.js:1544-1548@v0.9.2; code=main.js:1558-1563@v0.9.2; code=CHANGELOG_OLD.md:6@v0.9.2 -->

So sieht die Meldung aus:

```text
State attribute definition missing for : <Feld> with value : <Wert>
```
<!-- quelle: code=main.js:1547@v0.9.2 -->

### Was dahintersteckt

Der Adapter hat eine Liste mit allen WLED-Feldern, die er kennt. Darin steht für jedes Feld der Name, der Datentyp, die Rolle und ob du den Datenpunkt schreiben darfst. Bringt eine neue WLED-Firmware ein Feld mit, das in der Liste fehlt, legt der Adapter den Datenpunkt so an:

- Der Name ist der Feldname aus WLED.
- Der Datentyp richtet sich nach dem Wert, den WLED liefert.
- Der Datenpunkt ist nur lesbar. Schreiben über diesen Datenpunkt geht nicht.
<!-- quelle: code=main.js:1544-1563@v0.9.2; code=lib/stateAttr.js:1-60@v0.9.2 -->

Beispiele aus der Vergangenheit sind `cct`, `n` und `liveseg`. Sie kamen mit neuen WLED-Versionen und stehen inzwischen in der Liste.
<!-- quelle: issue=#322; issue=#423; issue=#479; code=CHANGELOG_OLD.md:2-6@v0.9.2 -->

Willst du ein solches Feld trotzdem setzen, schickst du es als JSON-Befehl über den Datenpunkt `action`. Fehlt dir ein Feld dauerhaft, melde es in einem [GitHub-Issue](https://github.com/DrozmotiX/ioBroker.wled/issues).
<!-- quelle: code=main.js:181-190@v0.9.3; issue=#15; issue=#487 -->

### Ältere Versionen

**Bis v0.7.0:** Die Meldung erschien als Warnung oder Fehler im normalen Log, teils mit dem Zusatz `Sentry disabled, error caught`. In v0.5.x konnte sich die Instanz danach beenden. Aktualisiere in diesem Fall den Adapter.
<!-- quelle: issue=#44; issue=#322; issue=#423; code=CHANGELOG_OLD.md:6@v0.9.2 -->

**Bis v0.9.2:** Auf der Stufe „debug“ steht die Meldung bei jeder Aktualisierung des Geräts erneut im Log, immer wieder für dasselbe Feld.
<!-- quelle: code=main.js:1544-1548@v0.9.2; issue=#917 -->

**Ab v0.9.3:** Der Adapter meldet jedes fehlende Feld nur einmal je Start ([#917](https://github.com/DrozmotiX/ioBroker.wled/issues/917)).
<!-- quelle: issue=#917; code=main.js:1724-1730@v0.9.3 -->

## Was bedeuten Warnungen zu falschem Datentyp oder fehlendem "val" beim Schreiben von States?

<!-- abschnitt: prio=A; gewicht=12; readme=missing; cluster=logs-install-05,logs-install-16,control-basics-10; features=info-device-online-state,migration-online-boolean,state-value-handling,state-root-light,state-segment-colors -->
<!-- muss beantworten: Erklärt erwartete Datentypen für on, ps und Farben und wie Blockly die Werte übergibt. -->

**Kurz:** ioBroker prüft jeden Wert, der in einen Datenpunkt geschrieben wird, gegen dessen Datentyp. Passt der Typ nicht, steht eine Warnung im Log. Kommt sie von deinem Skript, schreibst du den Wert im falschen Typ, zum Beispiel `"true"` als Text statt `true`. Kommt sie vom Adapter selbst, hilft ein Update.
<!-- quelle: issue=#611; issue=#189; issue=#11; issue=#52 -->

So sehen die Meldungen aus:

```text
State value to set for "wled.0.<MAC>.<State>" has to be type "boolean" but received type "string"
State value to set for "wled.0.<MAC>.<State>" has to be one of type "string", "number", "boolean" but received type "object"
State value to set is invalid for wled.0.<MAC>.<State>: The state is missing the required property val!
```
<!-- quelle: issue=#611; issue=#189; issue=#11 -->

Am Anfang der Log-Zeile steht, wer geschrieben hat. Steht dort `wled.<Instanz>`, kommt der Wert vom Adapter. Steht dort zum Beispiel `javascript.0`, kommt er aus deinem Skript.
<!-- quelle: issue=#611; issue=#11 -->

### Welchen Datentyp erwarten die Datenpunkte?

| Datenpunkt | Typ | Beispiel |
|---|---|---|
| `on` | Wahrheitswert (boolean) | `true` oder `false` |
| `bri` | Zahl | `0` bis `255` |
| `ps` | Zahl | `3` für Preset 3 |
| `pl` | Zahl | `1` für Playlist 1 |
| `transition` | Zahl | `7` |
| `seg.<Segment>.col.0`, `.1`, `.2` | Text mit Zahlen in eckigen Klammern | `"[255,0,0]"` oder mit Weißkanal `"[255,0,0,0]"` |
| `seg.<Segment>.col.0_HEX`, `.1_HEX`, `.2_HEX` | Text | `"#ff0000"` |
| `action` | Text mit JSON | `{"on":true,"bri":128}` als Text |
| `_info._online` | Wahrheitswert (boolean), nur lesbar | `true` oder `false` |
<!-- quelle: code=main.js:1559@v0.9.2; code=lib/stateAttr.js:52-78@v0.9.2; code=lib/stateAttr.js:222-257@v0.9.2; code=lib/stateAttr.js:277-281@v0.9.2; code=main.js:1080-1090@v0.9.2; code=main.js:1590-1594@v0.9.2; code=main.js:181-190@v0.9.3 -->

Die Typen von `on`, `bri`, `ps`, `pl` und `transition` legt der Adapter beim Anlegen nach dem Wert fest, den WLED liefert. Die Farb-Datenpunkte sind vom Typ „mixed“ und enthalten die Farbe als Text. Beim Schreiben nimmt der Adapter auch `"255,0,0"` ohne Klammern an.
<!-- quelle: code=main.js:1559@v0.9.2; code=lib/stateAttr.js:222-257@v0.9.2; code=main.js:312-330@v0.9.2 -->

### So schreibst du die Werte im richtigen Typ

Im Skript übergibst du Zahlen und Wahrheitswerte ohne Anführungszeichen, Farben als Text:

```js
setState('wled.0.<MAC>.on', true);                  // nicht 'true'
setState('wled.0.<MAC>.bri', 128);                  // nicht '128'
setState('wled.0.<MAC>.ps', 3);                     // nicht '3'
setState('wled.0.<MAC>.seg.0.col.0', '[255,0,0]');  // Text, keine Liste
setState('wled.0.<MAC>.seg.0.col.0_HEX', '#ff0000');
```
<!-- quelle: code=lib/stateAttr.js:52-78@v0.9.2; code=lib/stateAttr.js:222-257@v0.9.2; issue=#52 -->

In Blockly bestimmt der Block, den du an „steuere“ oder „aktualisiere“ anhängst, den Typ:

1. Für `on` nimmst du den Logik-Block „wahr“ oder „falsch“. Ein Text-Block mit `true` liefert Text.
2. Für `bri`, `ps` und `pl` nimmst du den Zahl-Block aus „Mathematik“. Ein Text-Block mit `3` liefert Text.
3. Für Farben nimmst du einen Text-Block mit `[255,0,0]` oder `#ff0000`. Ein Listen-Block liefert eine Liste, also den Typ „object“.
<!-- quelle: issue=#52; forum=429968; issue=#189 -->

![Übersicht: Der Logik-Block „wahr“ oder „falsch“ liefert boolean für on. Der Zahl-Block liefert eine Zahl für bri, ps, pl und transition. Ein Text-Block liefert Text für die Farb-Datenpunkte. Ein Text-Block mit true an on und ein Listen-Block an einer Farbe führen zu einer Warnung.](img/datentypen.svg)
<!-- quelle: code=main.js:1559@v0.9.2; code=lib/stateAttr.js:52-78@v0.9.2; code=lib/stateAttr.js:222-257@v0.9.2; issue=#52; issue=#189; issue=#611 -->

<!-- bild: screenshot Blockly mit „steuere wled.0.<MAC>.on mit wahr“ und „steuere wled.0.<MAC>.ps mit 3“ (Phase 5) -->

### Meldungen vom Adapter selbst

**Bis v0.9.2:** Ist ein Gerät nicht erreichbar, schreibt der Adapter `_info._online` als Text. Im Log steht dann `State value to set for "wled.0.<MAC>._info._online" has to be type "boolean" but received type "string"`. Du musst nichts ändern, die Meldung kommt vom Adapter.
<!-- quelle: code=main.js:1387-1392@v0.9.2; code=main.js:1590-1594@v0.9.2; issue=#788; issue=#794 -->

**Ab v0.9.3:** `_info._online` ist immer ein Wahrheitswert, die Meldung entfällt ([#788](https://github.com/DrozmotiX/ioBroker.wled/issues/788), [#794](https://github.com/DrozmotiX/ioBroker.wled/issues/794)).
<!-- quelle: issue=#788; issue=#794; code=main.js:1546-1562@v0.9.3 -->

Die Meldung `The state is missing the required property val!` und Typ-Meldungen zu Datenpunkten unter `_info` wie `_info.mac` kamen von Adapterversionen aus 2020 und 2021. Heute überspringt der Adapter leere Werte. Siehst du diese Meldungen noch, aktualisiere den Adapter.
<!-- quelle: issue=#11; issue=#189; code=main.js:1590-1594@v0.9.2 -->

### Datenpunkte, die sich mit v0.9.3 ändern

**Ab v0.9.3:** `seg.<Segment>.mi` (Segment spiegeln) ist ein Wahrheitswert und lässt sich schreiben ([#918](https://github.com/DrozmotiX/ioBroker.wled/issues/918)).
<!-- quelle: issue=#918; code=lib/stateAttr.js:501-506@v0.9.3; code=lib/stateAttr.js:500-503@v0.9.2 -->

**Ab v0.9.3:** `time` ist eine Zahl (Unix-Zeitstempel) und lässt sich schreiben, um die Uhrzeit des Geräts zu setzen ([#919](https://github.com/DrozmotiX/ioBroker.wled/issues/919)). Bis v0.9.2 ist `time` vom Typ „mixed“ und nur lesbar.
<!-- quelle: issue=#919; code=lib/stateAttr.js:450-455@v0.9.3; code=lib/stateAttr.js:450-454@v0.9.2 -->

## Was bedeuten die Fehler "Gerät nicht erreichbar" und "WebSocket was closed before the connection was established"?

<!-- abschnitt: prio=B; gewicht=4; readme=missing; cluster=logs-install-11,discovery-connection-17; features=admin-device-table,conn-watchdog,device-bonjour-autodiscovery,req-wled-firmware,conn-websocket -->
<!-- muss beantworten: Ordnet die Meldungen den Ursachen zu: Gerät aus, WLAN, zu viele WebSocket-Clients. -->

**Kurz:** Beide Meldungen heißen: Der Adapter erreicht das Gerät gerade nicht. Meist ist das Gerät aus, hat schlechten WLAN-Empfang oder eine neue IP-Adresse, oder es sind schon zu viele Programme per WebSocket mit ihm verbunden. Prüfe zuerst, ob sich die WLED-Oberfläche vom ioBroker-Netz aus öffnen lässt.
<!-- quelle: code=main.js:810-820@v0.9.2; code=main.js:1350-1415@v0.9.2; issue=#647; issue=#310; forum=373933; forum=769050 -->

### Die Meldungen und ihre Ursachen

| Meldung im Log | Stufe | Bedeutung | Häufige Ursache |
|---|---|---|---|
| `Unable to initialise 192.168.x.y will retry in scheduled interval !` | Warnung | Der Adapter hat das Gerät per HTTP gefragt und keine Antwort bekommen. Er versucht es später erneut. | Gerät aus oder ohne Strom, falsche IP-Adresse, WLAN weg |
| `Heartbeat of device 192.168.x.y failed, will try to reconnect` | Warnung | Ein Gerät, das schon verbunden war, antwortet bei der regelmäßigen Prüfung nicht mehr. | Gerät ausgeschaltet oder neu gestartet, WLAN-Abbruch |
| `Device 192.168.x.y unavailable (attempt 2/5), will retry in 60 seconds` | Info | Zählt die Wiederholungen nach einem Ausfall mit. | wie oben |
| `Websocket connection error : Error: WebSocket was closed before the connection was established` | Fehler | Der Adapter hat eine WebSocket-Verbindung aufgebaut, aber das Gerät hat sie nicht angenommen, bevor sie wieder geschlossen wurde. | Gerät aus oder überlastet, schlechtes WLAN, alle WebSocket-Plätze in WLED belegt |
| `Client 192.168.x.y does not support websocket, please consider upgrading your WLED firmware to >= 0.12. Switching to http-APi !` | Warnung | Die Firmware hat keinen WebSocket. Der Adapter fragt das Gerät nur per HTTP ab. | WLED älter als 0.12 |
<!-- quelle: code=main.js:1384@v0.9.2; code=main.js:1354@v0.9.2; code=main.js:1283-1292@v0.9.2; code=main.js:810-820@v0.9.2; issue=#647; extern=WLED:wled00/ws.cpp:223-230@v0.15.0 -->

Ein Fehler `Websocket connection error` bedeutet also nicht, dass der Adapter kaputt ist. Er steht auch dann auf der Stufe „Fehler“, wenn das Gerät einfach nur aus ist.
<!-- quelle: code=main.js:810-820@v0.9.2; code=main.js:1229-1234@v0.10.0; issue=#647 -->

### So prüfst du der Reihe nach

1. Öffne `http://192.168.x.y` im Browser eines Rechners im selben Netz wie ioBroker. Öffnet sich die WLED-Oberfläche nicht, liegt das Problem am Gerät oder im Netz, nicht am Adapter.
2. Prüfe die WLAN-Signalstärke in WLED unter „Info“ oder in ioBroker unter `wled.<Instanz>.<MAC>._info.wifi.signal`.
3. Prüfe `wled.<Instanz>.<MAC>._info.ws`. Der Wert zeigt, wie viele WebSocket-Verbindungen gerade bestehen. Ein ESP8266 hält höchstens 3, ein ESP32 höchstens 8. Schließ WLED-Oberflächen und Apps, die du nicht brauchst.
4. Hat das Gerät eine neue IP-Adresse bekommen, gib ihm im Router eine feste Adresse und lass den Adapter es neu finden.
5. Liegen ioBroker und WLED in getrennten Netzen (VLAN), muss die Verbindung von ioBroker zu WLED auf Port 80 erlaubt sein.
<!-- quelle: code=lib/stateAttr.js:347-349@v0.9.2; code=lib/stateAttr.js:492-495@v0.9.2; code=main.js:904-963@v0.9.2; extern=WLED:wled00/ws.cpp:223-230@v0.15.0; extern=ESPAsyncWebServer:src/AsyncWebSocket.h:50-54@v2.2.1; code=main.js:752@v0.9.2; code=main.js:1325@v0.9.2; forum=769050; issue=#310 -->

In der Gerätetabelle der Instanzeinstellungen steht ein Gerät, das nicht antwortet, auf rot. Grün heißt, `_info._online` ist `true`.
<!-- quelle: code=admin/index_m.html:28-95@v0.9.2; issue=#310 -->

**Ab v0.9.3:** Ein Ausfall steht nur noch einmal als Warnung im Log. Die Zeilen `Device … unavailable (attempt …)` und weitere `Unable to initialise …` stehen auf der Stufe „debug“ ([#903](https://github.com/DrozmotiX/ioBroker.wled/issues/903), [#788](https://github.com/DrozmotiX/ioBroker.wled/issues/788)). Antwortet eine IP-Adresse, die du von Hand hinzufügen willst, nicht, steht `Unable to initialise 192.168.x.y, device does not respond` im Log.
<!-- quelle: issue=#903; issue=#788; code=main.js:1541-1553@v0.9.3; code=main.js:1453-1458@v0.9.3 -->

**Ab v0.9.3:** Schreibst du einen Befehl an ein Gerät, das offline ist, steht `Device <MAC> (192.168.x.y) is offline, command for <State> discarded` als Warnung im Log ([#904](https://github.com/DrozmotiX/ioBroker.wled/issues/904)).
<!-- quelle: issue=#904; code=main.js:400-405@v0.9.3 -->

## Was sind die Sentry-Meldungen im Log?

<!-- abschnitt: prio=B; gewicht=2; readme=partial; cluster=logs-install-13; features=log-sentry,log-error-messages -->
<!-- muss beantworten: Erklärt, was gemeldet wird, wie man es abschaltet und warum Fehler doppelt erscheinen. -->

**Kurz:** Sentry ist ein Dienst, über den der Adapter Programmfehler an den Entwickler meldet, damit sie behoben werden können. Die Sentry-Zeilen im Log gehören immer zu einer Fehlermeldung direkt davor, es ist derselbe Fehler. Abschalten kannst du Sentry nur über ioBroker selbst, für den ganzen Host oder für eine Instanz, nicht in den Einstellungen des Adapters.
<!-- quelle: code=main.js:1652-1685@v0.9.2; code=io-package.json:151-156@v0.9.2; code=README.md:134-137@v0.9.2; interview=23; extern=plugin-sentry:README.md:18-28 -->

### Was gemeldet wird

Fängt der Adapter einen Programmfehler ab, schreibt er ihn ins Log und gibt ihn an das Sentry-Plugin von ioBroker weiter. Gemeldet wird die Fehlermeldung mit der Stelle im Code, also dasselbe, was auch im Log steht. Hast du ioBroker erlaubt, Diagnosedaten zu senden, kommt eine anonyme Kennung deiner Installation dazu, ohne Namen oder E-Mail-Adresse. Fehlende Datenpunkt-Beschreibungen meldet der Adapter seit v0.6.6 nicht mehr.
<!-- quelle: code=main.js:1652-1685@v0.9.2; code=README.md:134-137@v0.9.2; code=CHANGELOG_OLD.md:11-13@v0.9.2 -->

> [!NOTE]
> Die README nennt als gemeldete Inhalte auch „new device schemas“. Das stimmt seit v0.6.6 nicht mehr.
<!-- quelle: code=README.md:14@v0.9.2; code=CHANGELOG_OLD.md:11-13@v0.9.2 -->

### Die Meldungen im Log

Bis v0.9.2 steht jeder abgefangene Fehler zweimal im Log, zuerst als Fehler mit der Stelle im Code, zum Beispiel `[watchDog] TypeError: …`, und direkt danach eine der beiden Zeilen:

| Zeile | Stufe | Bedeutung |
|---|---|---|
| `[Error caught and sent to Sentry, thank you for collaborating!] <Fehler>` | Info | Sentry ist aktiv, der Fehler wurde gemeldet. |
| `Sentry disabled, error caught : <Fehler>` | Fehler | Sentry ist abgeschaltet, gemeldet wurde nichts. Die Zeile wiederholt nur den Fehler davor. |
<!-- quelle: code=main.js:1652-1660@v0.9.2; code=main.js:1671-1685@v0.9.2; issue=#172; issue=#403 -->

Werte nur die erste Zeile aus. Um die Ursache zu finden, hilft die Seite [Warum startet der Adapter nach einem Update nicht oder reagiert nicht mehr?](../04.fehlerbehebung/01.verbindung-und-start.md#adapter-not-start-stop-responding)
<!-- quelle: code=main.js:1652-1685@v0.9.2 -->

**Ab v0.9.3:** Jeder Fehler steht nur einmal im Log. Die Übergabe an Sentry steht auf der Stufe „debug“: `Error sent to Sentry: <Fehler>` oder `Sentry disabled, error not sent: <Fehler>` ([#913](https://github.com/DrozmotiX/ioBroker.wled/issues/913)). Ein Befehl an ein Gerät, das offline ist, ist kein Programmfehler mehr und geht nicht mehr an Sentry ([#904](https://github.com/DrozmotiX/ioBroker.wled/issues/904)).
<!-- quelle: issue=#913; code=main.js:1853-1866@v0.9.3; issue=#904; code=main.js:400-405@v0.9.3 -->

### So schaltest du Sentry ab

Sentry ist ein Plugin von ioBroker, nicht vom WLED-Adapter. Du schaltest es auf der Konsole des ioBroker-Hosts ab:

- nur für den WLED-Adapter: `iobroker plugin disable sentry --instance wled.0`
- für den ganzen Host: `iobroker plugin disable sentry`
<!-- quelle: extern=plugin-sentry:README.md:18-28; interview=23 -->

Alternativ setzt du den Datenpunkt `system.adapter.wled.0.plugins.sentry.enabled` auf `false`. Im Log der Instanz steht danach eine Meldung, dass Sentry abgeschaltet ist. Mehr dazu in der [Beschreibung des Sentry-Plugins](https://github.com/ioBroker/plugin-sentry#readme).
<!-- quelle: extern=plugin-sentry:README.md:18-28 -->

> [!TIP]
> Lass Sentry eingeschaltet, wenn es für dich in Ordnung ist. Fehler, die nicht gemeldet werden, findet der Entwickler nur, wenn du sie selbst in einem [GitHub-Issue](https://github.com/DrozmotiX/ioBroker.wled/issues) meldest.
<!-- quelle: code=README.md:134-137@v0.9.2; extern=ioBroker.js-controller:README.md:499 -->
