## Why doesn't the adapter start after an update, or why does it stop responding?

<!-- abschnitt: prio=A; gewicht=9; readme=missing; cluster=logs-install-04; features=log-error-messages,conn-watchdog -->
<!-- muss beantworten: Zählt die bekannten Ursachen mit Log-Zeilen und die Schritte zur Behebung auf. -->

**In short:** Look at the log of the instance `wled.<instance>` first. The known causes are: requirements such as the Node.js version not met, an incompletely installed update, bugs in older adapter versions, and in v0.9.2 a polling interval of 0 or devices that were added after the start. The table below matches the log lines to their causes.
<!-- quelle: code=package.json:30-32@v0.9.3; issue=#270; issue=#400; issue=#263; issue=#44; issue=#924; issue=#901 -->

### How to proceed

1. In Admin, open the "Log" tab and look for the lines of the instance `wled.<instance>` and the `host.<host>` lines right after the instance starts. If the adapter doesn't start at all, the error is often in the host lines with `Caught by controller`.
2. Compare the lines with the table below and follow the solution.
3. Restart the instance afterwards.
4. If the error remains, set the log level of the instance to "debug", restart it and attach the log excerpt to a [GitHub issue](https://github.com/DrozmotiX/ioBroker.wled/issues). Replace IP and MAC addresses first.
<!-- quelle: issue=#270; issue=#44; issue=#263 -->

### Known causes and log lines

![Decision tree: check in order whether the installation reports a Node.js version that is too old, whether "Cannot find module" is in the log, whether messages from old versions appear, whether many "Unable to initialise" lines come, whether the load is high without an error message, or whether a device no longer responds after an outage. If nothing fits, attach a debug log to a GitHub issue.](img/adapter-startet-nicht.svg)
<!-- quelle: code=package.json:30-32@v0.9.2; issue=#270; issue=#400; issue=#263; issue=#44; code=main.js:1384@v0.9.2; code=main.js:1307@v0.9.2; issue=#924; code=main.js:80-84@v0.9.2; issue=#901 -->

| Log line (excerpt) | Cause | Solution |
|---|---|---|
| No start after the update; the installation reports a Node.js version that is too old | In v0.9.2 the adapter needs Node.js 20 or newer, js-controller 6.0.11 or newer and Admin 7.6.17 or newer. | Update Node.js, js-controller or Admin. |
| `Caught by controller[0]: Error: Cannot find module 'axios'` | The update wasn't installed completely; a library of the adapter is missing. | Install the adapter again in the "Adapters" tab, or install a newer version. |
| `[handleStates] TypeError: Cannot read property 'initialized' of undefined` | Bug in versions before v0.6.7, fixed in v0.6.7. | Update the adapter. |
| `Caught by controller[0]: State attribute definition missing for …`, after which the instance stops | Bug in v0.5.x. Since v0.7.1 the message is only a debug message without consequences. | Update the adapter. |
| Many lines `Unable to initialise 192.168.x.y will retry in scheduled interval !` and `Device 192.168.x.y unavailable (attempt n/5), will retry in … seconds` | A device is switched off or can't be reached. The adapter keeps running, but the log fills up with every attempt. | Switch the device on, or delete it if you no longer use it. |
| After every error, a second line `Sentry disabled, error caught : …` | The adapter reports every error twice. It is the same error. | Only look at the first line. |
| No error message, but the adapter stops responding and the load is high | "Intervall in seconds" is set to 0. The requests then run without a pause. | Set the interval to at least 1 second; the default is 30 seconds. |
| No error message, but a device no longer responds after an outage | The device was added after the adapter started, via "Discover new devices", by IP, or because the Bonjour search only found it later. In v0.9.2 no monitoring starts for such devices, so they don't reconnect after an outage. | Restart the instance. |
<!-- quelle: code=package.json:30-32@v0.9.2; code=io-package.json:160-170@v0.9.2; issue=#270; issue=#400; issue=#263; code=main.js:1384@v0.9.2; code=main.js:1284-1291@v0.9.2; issue=#788; code=main.js:1652-1684@v0.9.2; issue=#913; code=main.js:1307@v0.9.2; code=admin/index_m.html:258@v0.9.2; code=io-package.json:175@v0.9.2; issue=#924; code=main.js:80-84@v0.9.2; issue=#901 -->

The two lines about `State attribute definition missing` and `Cannot read property 'initialized'` come from old versions. If you still see them today, you are running an old adapter version.
<!-- quelle: issue=#44; issue=#400; code=CHANGELOG_OLD.md:6@v0.9.2; code=main.js:1544-1548@v0.9.2 -->

> [!NOTE]
> The setting "Max retry attempts" applies to all devices of the instance together. There is no setting per device.
<!-- quelle: interview=6; code=main.js:1348@v0.9.3 -->

### From v0.9.3

**From v0.9.3:** The adapter needs Node.js 22 or newer and Admin 7.6.20 or newer. Check this before updating.
<!-- quelle: code=package.json:30-32@v0.9.3; code=io-package.json:160-169@v0.9.3 -->

**From v0.9.3:** If the polling interval is below 1 second or the number of retries is invalid, the adapter replaces it with the default at startup and warns once: `Invalid polling interval "0", using 30 seconds` or `Invalid number of retry attempts "0", using 5` ([#924](https://github.com/DrozmotiX/ioBroker.wled/issues/924)). Correct the setting so that the warning goes away.
<!-- quelle: issue=#924; code=main.js:66-80@v0.9.3 -->

**From v0.9.3:** An outage appears in the log as a single warning, for example `Unable to initialise 192.168.x.y will retry in scheduled interval !` or `Heartbeat of device 192.168.x.y failed, will try to reconnect`. The further attempts only appear at the level "debug" ([#903](https://github.com/DrozmotiX/ioBroker.wled/issues/903), [#788](https://github.com/DrozmotiX/ioBroker.wled/issues/788)).
<!-- quelle: issue=#903; issue=#788; code=main.js:1514-1520@v0.9.3; code=main.js:1546-1553@v0.9.3 -->

**From v0.9.3:** Every error appears in the log only once. The hand-over to Sentry only appears at the level "debug" ([#913](https://github.com/DrozmotiX/ioBroker.wled/issues/913)).
<!-- quelle: issue=#913; code=main.js:1853-1866@v0.9.3 -->

**From v0.9.3:** Devices that are added after the start are monitored as well and reconnect after an outage without a restart ([#901](https://github.com/DrozmotiX/ioBroker.wled/issues/901)). `_info._online` becomes `false` if a device doesn't answer for two polling intervals ([#900](https://github.com/DrozmotiX/ioBroker.wled/issues/900)).
<!-- quelle: issue=#901; code=main.js:980-984@v0.9.3; issue=#900; code=main.js:1786-1795@v0.9.3 -->

**From v0.9.3:** The adapter discards a command to a device that is offline, with the warning `Device <MAC> (192.168.x.y) is offline, command for <State> discarded` ([#904](https://github.com/DrozmotiX/ioBroker.wled/issues/904)). `on` and `bri` keep their last value when the device goes offline and when the adapter starts ([#899](https://github.com/DrozmotiX/ioBroker.wled/issues/899)).
<!-- quelle: issue=#904; code=main.js:400-405@v0.9.3; issue=#899 -->

**From v0.10.0:** The setting is called "Polling interval". You find it in the instance settings on the "Settings" tab under "Connection", next to "Max retry attempts". The form only accepts an interval of 1 second or more, and 1 to 20 for the retries ([#266](https://github.com/DrozmotiX/ioBroker.wled/issues/266)).
<!-- quelle: issue=#266; code=admin/jsonConfig.json:36-65@v0.10.0; code=admin/i18n/en/translations.json:4-7@v0.10.0 -->

**From v0.10.0:** If you write a command to a device that counts as offline, the adapter tries to reach it right away instead of waiting for the next check. If the device answers, the command goes out. Only if it doesn't answer does the adapter discard the command with the warning above ([#939](https://github.com/DrozmotiX/ioBroker.wled/issues/939)). There are at least 5 seconds between two such attempts for the same device.
<!-- quelle: issue=#939; code=main.js:428-445@v0.10.0; code=main.js:2058-2086@v0.10.0; code=main.js:34@v0.10.0 -->
